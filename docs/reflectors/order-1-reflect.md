## 悪かった点

### 1. 問題の本質理解に時間がかかった
- **症状**: フォルダ選択ダイアログが開かない
- **最初の判断ミス**: File System Access APIの問題と判断し、input要素方式への大幅な書き換えを実施
- **実際の原因**: Playwright MCPの仕様（自動インターセプト）
- **影響**: 不要なコード変更に約1時間を費やした

**教訓**: 
- ブラウザ自動化ツール特有の制約を事前に理解すべきだった
- 「動かない」→「すぐコード変更」ではなく、まず環境・ツールの仕様を確認すべき

### 2. 代替MCP（Chrome DevTools）への切り替えタイミングが遅かった
- Playwright MCPで問題が発生した時点で、すぐに別のMCPを試すべきだった
- 結果的に、Chrome DevTools MCPでは最初から正常に動作した

**教訓**:
- 特定のツールで問題が発生したら、早めに代替手段を試す
- 「ツールの問題」と「コードの問題」を切り分ける

### 3. 空フォルダ対応のロジックが重複していた
- `FileSystemAdapter.loadDirectory()`で既にプレースホルダーファイルを作成
- `RepomixCore.openFolder()`でも再度チェック（実際には実行されない）
- 不要なコードが残った状態

**教訓**:
- 機能の実装場所を明確にする
- レイヤー間の責務を整理する

### 4. デバッグログの削除漏れ
- 開発中に追加したconsole.logが本番コードに残っていた
- コードレビューで気づいて削除

**教訓**:
- デバッグログは一時的なものとして明示的にマーク
- コミット前に不要なログを削除するチェックリストを作成

### 5. ブラウザキャッシュの影響
- コード変更後もブラウザが古いコードを実行
- ハードリロードが必要だった

**教訓**:
- 開発サーバー再起動時は、ブラウザもリロードする習慣をつける
- Viteの設定でキャッシュを無効化する選択肢もある

## 技術的な学び

### 1. File System Access API
- `showDirectoryPicker()`は最新のブラウザでサポート
- 権限管理が厳密（読み取り・書き込み別々）
- Safari未サポート（2025年11月時点）

### 2. Playwright MCPの特性
- ファイル選択ダイアログを自動的にインターセプト
- `Page.setInterceptFileChooserDialog()`がデフォルトで有効
- 手動操作には向かない、自動テストに特化

### 3. Chrome DevTools MCPの特性
- Chrome DevTools Protocolを使用
- 手動操作とMCP操作の混在が可能
- Playwrightより柔軟だが、機能は限定的

### 4. Monaco Editorの操作
- `window.monaco.editor.getEditors()`で全エディターインスタンスを取得
- `editor.setValue()`で内容を設定
- Reactの状態管理と統合されている

### 5. 空フォルダ検出の実装
- `FileSystemDirectoryHandle.values()`でエントリを取得
- フィルタ適用後のエントリ数でチェック
- プレースホルダーファイルをディスクに保存

### 6. UNMIX処理の順序
- **修正前**: parse → FileManager更新 → refresh
  - 問題: 新規ファイルがメモリ上にのみ存在
- **修正後**: parse → ディスクへ書き込み → ディスクから再読み込み
  - 解決: 新規ファイルが実際のディスクに保存される
