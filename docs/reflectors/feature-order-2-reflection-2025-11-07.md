## タスク概要

**背景:**
- order-1 で実装した File System Access API を使ったローカルファイル操作機能が、localhost では動作するが HTTPS 環境で挙動が異なるという報告があった
- 原因の特定と、デプロイ後のビルド識別を容易にするための改善が必要だった

**目的:**
1. localhost と HTTPS 環境の動作差異の原因を特定する
2. 診断ログを追加して実行時の環境情報を可視化する
3. ビルド時にバージョン情報を埋め込み、デプロイ後の確認を容易にする
4. リリースプロセスを自動化するスクリプトを作成する

**制約:**
- ユーザーは本番環境での検証が必要
- キャッシュや Service Worker による影響も考慮する必要がある
- コミットは慎重に行う（途中段階では禁止）

## 実行トレース

### Step 1: 問題の調査と診断ログ追加
**実行内容:**
- `src/adapters/FileSystemAdapter.ts` に診断ログを追加
  - `selectFolder()` で isSecureContext, inIframe, showDirectoryPicker の有無を確認
  - `verifyPermission()` で permission API の動作を詳細にログ出力
  - `saveFromManager()` でファイル処理の詳細をログ出力

**判断理由:**
- 環境差異（localhost vs HTTPS）を可視化するため
- File System Access API の利用可能性と権限フローを追跡するため

**ツール使用:** read_file, replace_string_in_file

**結果:**
- 成功: ログが正しく挿入され、TypeScript/lint エラーも修正
- ユーザーが HTTPS 環境で実行したログから、権限が正常に付与され、placeholder ファイルも作成されていることが確認できた

**気づき:**
- 問題の根本原因は File System Access API のサポートではなく、キャッシュや自動化ツール (MCP) の干渉である可能性が高い

### Step 2: `RepomixCore.ts` に UNMIX フローの診断ログ追加
**実行内容:**
- `unmix()` メソッド内の XML パース、saveFromManager、loadToManager の各フェーズにログを追加

**判断理由:**
- UNMIX 時のファイル書き込み・読み込みフローを追跡し、データの流れを可視化する

**結果:**
- 成功: ログが追加され、フロー全体が可視化された

### Step 3: ビルド時バージョン埋め込み
**実行内容:**
- `vite.config.ts` に `__APP_VERSION__`, `__APP_COMMIT__`, `__BUILD_TIME__` を define で追加
- `src/main.tsx` で document.title にバージョンとコミットを追加
- `package.json` に `standard-version` を追加し、`release` スクリプトを定義

**判断理由:**
- デプロイ後のビルドが正しいかを簡単に確認できるようにする
- キャッシュによる「古いビルドが表示される」問題に対処する

**結果:**
- 成功: ビルド時に自動的にバージョン情報が埋め込まれ、ブラウザタブのタイトルで確認可能になった
- TypeScript チェックも通過

### Step 4: `release.sh` スクリプト作成
**実行内容:**
- リリースフローを自動化するシェルスクリプトを作成
  - main ブランチでの実行を禁止
  - 作業ツリーのクリーンチェック
  - standard-version による version bump と tag 作成
  - push と main へのマージをデフォルトで実行（--no-push, --no-merge で抑止可能）
  - ビルド実行

**判断理由:**
- 手動でのリリース手順のミスを防ぐ
- 一貫したリリースフローを確立する

**結果:**
- 成功: スクリプトが作成され、実行権限も付与された
- ヘルプ表示も正しく動作することを確認

**気づき:**
- 作業ツリーがクリーンでないと実行できないため、先に release.sh 自体をコミットする必要がある

### Step 5: Git タグと本番ビルドの運用方針確認
**実行内容:**
- ユーザーと以下の運用方針を確認・提案:
  - Git タグはリポジトリ肥大化にほぼ影響しない（軽量な参照のため）
  - 本番ビルドは「タグがついたコミット」からビルドするのが安全で再現性が高い
  - CI で tag push をトリガーにビルド・デプロイする運用を推奨

**結果:**
- ユーザーが理解し、承認

## 学んだ教訓

### 教訓1: 環境差異のデバッグは「可視化」が最優先
- **状況:** localhost と HTTPS で動作が異なるという報告
- **問題:** 何が違うのか、どこで失敗しているのかが不明
- **解決策:** 診断ログを追加して、環境情報（isSecureContext, API の有無）、権限フロー、ファイル操作の詳細を可視化
- **教訓:** ブラウザ環境の差異や API サポート状況は、推測ではなくログで確認する。特に secure context 要件がある API では必須。

### 教訓2: デプロイ後の「何が動いているか」を確認できる仕組みが必須
- **状況:** 本番環境で「古い動作」が見られるが、原因がキャッシュかコードかが不明
- **問題:** デプロイしたビルドのバージョンが確認できない
- **解決策:** ビルド時にバージョン、コミット SHA、ビルド時刻を埋め込み、document.title と console に出力
- **教訓:** SPA では Service Worker やブラウザキャッシュによる「古いビルドが表示される」問題が頻発する。ビルド識別子の埋め込みは必須。

### 教訓3: リリースフローの自動化は安全機構とセットで
- **状況:** 手動リリースでミスが発生しやすい（main で実行、タグ忘れ、ビルド忘れなど）
- **解決策:** release.sh で一連のフローを自動化し、main での実行禁止、作業ツリーチェック、テスト実行を組み込む
- **教訓:** 自動化スクリプトは「何をしてはいけないか」を明示的にチェックすることで安全性が向上する。

### 教訓4: Git タグは軽量で、本番ビルドの基準として最適
- **状況:** リリースバージョンを管理する方法を検討
- **解決策:** Git タグをバージョン管理の基準とし、CI でタグ push をトリガーにビルド・デプロイ
- **教訓:** タグはほぼゼロコストで、特定コミットを固定できるため再現性が高い。本番ビルドは必ずタグから行うべき。

### 教訓5: Wisdom 抽出は「何を抽出するか」を明確にする
- **状況:** ACE プロンプトを実行したが、ACE 自体の Tips を抽出してしまった
- **問題:** feature/order-2 の実装内容ではなく、ACE の使い方に関する内容を生成
- **解決策:** 抽出対象（feature/order-2 の作業内容）を明確にし、source を正しく設定する
- **教訓:** 振り返りの「何について振り返るか」を明確にしないと、メタな内容（ツールの使い方など）を抽出してしまう。
